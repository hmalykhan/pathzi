● Pathzi Analytics Module — Complete Plan                                                                                                                                                     
                                                                                                                                                                                              
  1. Goal in one line                                                                                                                                                                         
   
  Track every meaningful user action (views, swipes, saves, clicks, consent) without slowing down the app, and let admins query it all from one place.                                        
                                                                                                                                                                                            
  ---                                                                                                                                                                                         
  2. Folder structure (what we'll create)                                                                                                                                                   
                                         
  - analytics/ — new Django app
    - models.py — UserActivity + ProviderLead tables                                                                                                                                          
    - constants.py — fixed list of activity type names
    - services.py — helper functions (log_activity, report functions)                                                                                                                         
    - tasks.py — Celery background tasks                                                                                                                                                      
    - views.py — public endpoint + admin report endpoints                                                                                                                                     
    - urls.py — routes                                                                                                                                                                        
    - serializers.py — input validation                                                                                                                                                     
    - admin.py — Django admin registration                                                                                                                                                    
    - permissions.py — staff-only checks for admin reports                                                                                                                                  
    - migrations/ — DB schema files                                                                                                                                                           
  
  ---                                                                                                                                                                                         
  3. Database — what tables we add                                                                                                                                                          
                                                                                                                                                                                              
  UserActivity (the main log table)
                                                                                                                                                                                              
  - user → FK to User (nullable, SET_NULL for GDPR)                                                                                                                                           
  - career → FK to CareerJob (nullable, SET_NULL)
  - route_id → integer (nullable)                                                                                                                                                             
  - activity_type → string (e.g. "career_viewed")                                                                                                                                           
  - activity_value → text (e.g. career name)                                                                                                                                                  
  - metadata → JSON (free-form extra data)                                                                                                                                                    
  - created_at → timestamp
                                                                                                                                                                                              
  Indexes:                                                                                                                                                                                  
  - (activity_type, created_at) — for global reports                                                                                                                                          
  - (career, activity_type) — for per-career reports                                                                                                                                        
  - (user, activity_type) — for per-user reports    
  - (user, career, activity_type) — for cross-cutting queries                                                                                                                                 
                                                             
  ProviderLead (separate, for GDPR-safe consent)                                                                                                                                              
                                                                                                                                                                                              
  - user → FK to User
  - career → FK to CareerJob                                                                                                                                                                  
  - provider_name → string                                                                                                                                                                  
  - provider_type → string                                                                                                                                                                    
  - contact_email → string
  - consent_at → timestamp                                                                                                                                                                    
                                                                                                                                                                                            
  ---
  4. The activity types we'll support
                                                                                                                                                                                              
  Stored as strings (flexible — add new ones anytime without migration):
                                                                                                                                                                                              
  - career_viewed                                                                                                                                                                           
  - career_swiped_right                                                                                                                                                                       
  - career_swiped_left                                                                                                                                                                      
  - career_saved
  - career_unsaved
  - career_explored                                                                                                                                                                           
  - career_unexplored
  - route_viewed                                                                                                                                                                              
  - route_clicked                                                                                                                                                                           
  - provider_link_clicked
  - connect_button_clicked
  - consent_given
  - search_performed                                                                                                                                                                          
   
  All listed in analytics/constants.py so no typos anywhere in code.                                                                                                                          
                                                                                                                                                                                            
  ---
  5. How events get logged — two lanes
                                                                                                                                                                                              
  Lane A — single-task-per-event (backend-fired)
                                                                                                                                                                                              
  For server-side actions that already hit our API:                                                                                                                                           
                                                                                                                                                                                              
  - save / unsave / explore / unexplore endpoints                                                                                                                                             
  - Bulk interactions                                                                                                                                                                       
  - Search
                                                                                                                                                                                              
  Flow:
  - Endpoint runs → calls log_activity(...)                                                                                                                                                   
  - log_activity fires a Celery task (task.delay())                                                                                                                                         
  - Worker writes one UserActivity row in the background
                                                                                                                                                                                              
  Lane B — buffered-queue-with-batch-flush (frontend-fired)                                                                                                                                   
                                                                                                                                                                                              
  For high-volume UI events the server doesn't know about:                                                                                                                                    
                                                                                                                                                                                            
  - Views, swipes, route clicks, link opens                                                                                                                                                   
                                                                                                                                                                                            
  Flow:                                                                                                                                                                                       
  - Frontend sends batch (1–200 events) to POST /analytics/activity/                                                                                                                        
  - Endpoint pushes them to a Redis list (~5 ms)                                                                                                                                              
  - Celery beat task wakes up every 5 seconds   
  - Grabs up to 500 events, runs bulk_create (one INSERT)                                                                                                                                     
                                                                                                                                                                                              
  ---                                                                                                                                                                                         
  6. Endpoints we'll build                                                                                                                                                                    
                                                                                                                                                                                              
  Public (mobile/frontend uses these)                                                                                                                                                       
                                                                                                                                                                                              
  - POST /analytics/activity/
    - Body: { "events": [...] } — accepts 1 to 200 events                                                                                                                                     
    - Drops into Redis queue                                                                                                                                                                  
    - Returns immediately ({"queued": N})
  - POST /analytics/consent/                                                                                                                                                                  
    - For consent_given only                                                                                                                                                                  
    - Synchronous write to ProviderLead
    - Returns confirmation                                                                                                                                                                    
                                                                                                                                                                                            
  Admin (staff-only reports)                                                                                                                                                                  
                                                                                                                                                                                            
  - GET /admin/analytics/overview/ — totals, last 30 days                                                                                                                                     
  - GET /admin/analytics/career/<id>/ — single career's stats
  - GET /admin/analytics/user/<id>/ — single user's history                                                                                                                                   
  - GET /admin/analytics/top/<activity_type>/ — top-20 careers for that action                                                                                                                
  - GET /admin/analytics/like-vs-skip/ — engagement ratio per career                                                                                                                          
  - GET /admin/analytics/timeseries/?type=&days= — chart data                                                                                                                                 
  - GET /admin/analytics/routes/ — most-clicked education routes                                                                                                                              
  - GET /admin/analytics/providers/ — most-clicked providers                                                                                                                                  
                                                                                                                                                                                            
  ---                                                                                                                                                                                         
  7. Background processing setup                                                                                                                                                            
                                                                                                                                                                                              
  - Celery task: record_activity_task(payload) — Lane A worker
  - Celery beat task: flush_activity_queue() — Lane B worker                                                                                                                                  
  - Schedule: every 5 seconds (added to CELERY_BEAT_SCHEDULE in settings.py)                                                                                                                
  - Worker command: celery -A pathzi worker -B (worker + beat in one process)                                                                                                                 
  - Redis key for queue: analytics:queue

Where we hook into existing code

  - careers/views.py → CareersView.unsave → log career_unsaved
  - careers/views.py → CareersView.explore → log career_explored                                                                                                                              
  - careers/views.py → CareersView.unexplore → log career_unexplored                                                                                                                          
  - careers/services/interactions_bulk.py → loop over the 4 ID lists, one log per item
  - geo_search/views.py → NearbySearchAPI.post → log search_performed                                                                                                                         
                                                                                                                                                                                              
  No existing logic changes. Pure additions.                                                                                                                                                  
                                                                                                                                                                                              
  ---                                                                                                                                                                                       
  9. The reports we'll be able to answer
                                                                                                                                                                                              
  Per career
                                                                                                                                                                                              
  - How many people viewed it                                                                                                                                                                 
  - How many liked it (right swipe)
  - How many skipped it (left swipe)                                                                                                                                                          
  - How many saved / unsaved / explored / unexplored it                                                                                                                                     
  - Which routes were clicked from it                                                                                                                                                         
  - Which providers were opened from it
                                                                                                                                                                                              
  Per user                                                                                                                                                                                    
   
  - What this user saved / unsaved / viewed / explored / liked / skipped                                                                                                                      
  - Their full action timeline                                                                                                                                                              
                                                                                                                                                                                              
  Global
                                                                                                                                                                                              
  - Total users, total views, total swipes, total saves                                                                                                                                     
  - Top 20 most-liked careers
  - Top 20 most-skipped careers                                                                                                                                                               
  - Top 20 most-viewed careers
  - Top 20 most-saved careers                                                                                                                                                                 
  - Most-clicked routes (apprenticeship/college/university/etc)                                                                                                                             
  - Most-clicked providers (UCAS, employers, etc)                                                                                                                                             
  - Activity by day (for trend charts)                                                                                                                                                        
  - Users who consented to be contacted (separate ProviderLead table)                                                                                                                         
                                                                                                                                                                                              
  ---                                                                                                                                                                                       
  10. GDPR safety measures                                                                                                                                                                    
                                                                                                                                                                                            
  - user field is nullable + SET_NULL — deleting a user anonymises their history, doesn't erase analytics
  - metadata is sanitised — emails/phones stripped from frontend payloads (except in consent_given flow)                                                                                      
  - ProviderLead is the only place identifiable contact data lives — kept separate from analytics                                                                                             
  - Retention purge — Celery task deletes events older than N days (configurable, e.g. 365)                                                                                                   
  - Consent endpoint is synchronous + audit-logged so we can prove when consent was given                                                                                                     
                                                                                                                                                                                              
  ---                                                                                                                                                                                         
  11. Failure handling                                                                                                                                                                        
                                                                                                                                                                                              
  - log_activity wrapped in try/except — if Redis or Celery is down, the user's actual request still succeeds
  - Bad events in the Redis queue are logged and skipped (don't break the whole batch)                                                                                                        
  - Celery task retries with backoff if Postgres write fails                                                                                                                                  
  - Redis AOF persistence enabled on DigitalOcean — survives Redis restart                                                                                                                    
  - Frontend buffers events locally — flushes on next launch if network was down                                                                                                              
                                                                                                                                                                                              
  ---                                                                                                                                                                                         
  12. Performance characteristics                                                                                                                                                             
                                                                                                                                                                                              
  - Request thread cost per event: ~1 ms (just an LPUSH or task.delay())
  - Postgres writes: batched, one INSERT per ~500 events                                                                                                                                      
  - DB load: smoothed, no spikes during user bursts                                                                                                                                           
  - Frontend response time: unchanged for /save/, /explore/, etc.                                                                                                                             
  - No interference with /careers/, /billing/, /accounts/ traffic                                                                                                                             
                                                                                                                                                                                              
  ---                                                                                                                                                                                         
  13. Testing plan                                                                                                                                                                            
                                                                                                                                                                                            
  - Unit tests for each report function
  - Integration test: fire event → verify it lands in DB after flush                                                                                                                          
  - Load test: simulate 200 events × 100 users
  - GDPR test: delete user → confirm activity rows still exist but user is null                                                                                                               
  - Consent test: confirm ProviderLead is only written on explicit consent
